# ちょこっとインハウス サービスページ用プロダクト整理

更新日: 2026-08-28  
用途: サービスページLPの企画・構成・コピーを作る前の社内整理  
ステータス: LP実装前の確定版（公開前QAは別途必要）

## 1. このドキュメントの役割

このドキュメントは、リポジトリに定義されているプロダクトの内容を、サービスページで説明できる単位に整理したものです。参考LPの構造を踏まえ、LP実装前に確認するページ構造・デザイン方針・確定文言をここで固定します。

LPでは、AIの機能を並べるのではなく、広告運用の担当者が「数字を見たあとに、何を確認し、何を実行するか」まで進められるサービスとして伝えます。広告設定をAIに丸投げするサービスではありません。

現時点で確認できる情報を次の3つに分けています。

- **現行の正本**: `REQUIREMENTS.md`、`DESIGN.md`、`docs/architecture.md`、`docs/adk-design.md`などに定義された仕様
- **デモ・画面上の表現**: `apps/web/src/lp.tsx`、`fixtures/demo/`などにある説明や合成データ
- **公開前に要確認の事項**: 本番接続、顧客実績、料金表示、対応媒体の表現など

## 2. プロダクトの定義

### サービス名

- 顧客向け名称: **ちょこっとインハウス**
- 内部プロダクト名: **AdOps Advisor**

### 一言でいうと

> 自社で広告運用するチームのために、広告データを読み取り、原因仮説・改善案・人間向け作業手順まで作るAI広告相談役。

### LPで使える短い説明

> 広告管理画面の数字を、次に確認すること・実行することへ変える。

### 価値の中心

広告運用で困るのは、数字が見えないことだけではありません。

- CPAやROASが変化したとき、最初にどこを見るか迷う
- 分析やレポート作成に時間がかかり、改善施策に手が回らない
- 施策の優先順位や原因仮説を、社内に説明しづらい
- AIを使っても、自社の広告データとつながっていなければ実務の判断に使いにくい
- 広告設定を自動で変えられることには、誤操作や責任分界への不安がある

ちょこっとインハウスは、広告データと運用担当者の判断の間を埋めます。

## 3. 想定する顧客

### 初期ICP

| 項目 | 想定 |
| --- | --- |
| 企業 | 自社で広告運用を行う中小企業 |
| 主な業種 | 自社EC / D2C / 小規模BtoB |
| 月間広告費 | 50万〜500万円程度 |
| 運用体制 | 社内に広告成果の責任者または担当者がいる |
| 媒体 | Google Adsを先行。Meta Ads / Yahoo Adsは後続フェーズ |
| 課題 | 分析、優先順位付け、施策化、社内説明、振り返り |
| 導入姿勢 | read-onlyのデータ連携と、人間の確認・承認を受け入れられる |

### LPで刺さりやすい担当者

- 広告運用を兼任しているマーケティング担当者
- 自社広告の数字を見ているが、改善判断に確信が持てない責任者
- 代理店への相談待ちを短くしたい事業責任者
- 広告運用の状況を経営・上長へ説明する必要がある担当者
- 広告運用を始めたいが、初期設計と計測の抜け漏れが不安な担当者

### 初期対象から外す顧客

- AIによる自動入札、予算変更、広告入稿を必須とする企業
- 代理店に完全委託し、自社で判断・実行する担当者がいない企業
- 複数顧客を運用する代理店向けのマルチクライアント運用
- 高度なエンタープライズBIや独自KPI基盤を最初から必要とする企業

## 4. 顧客が抱える問題

### 問題の構造

広告管理画面には数字があります。しかし、数字だけでは次の行動になりません。

1. 数値の変化に気づく
2. どの指標を追加で見るか判断する
3. 原因の候補を切り分ける
4. 優先度を決める
5. 担当者が広告管理画面やLPで実行する
6. 実施後の変化を記録し、次の判断へつなげる

このうち、特に時間と経験が必要なのが2〜6です。ちょこっとインハウスは、ここをAIと人間の分担で支援します。

### 顧客の言葉に置き換えた悩み

- 「CPAが悪化した理由を、どこから確認すればいいか分からない」
- 「レポートは作れるが、次にやることまで決められない」
- 「施策の候補は出るが、何から試すべきか説明できない」
- 「担当者が休むと、判断の経緯や確認事項が分からなくなる」
- 「広告設定をAIに触らせるのは怖いが、分析だけでは物足りない」
- 「新しいキャンペーンを始めたいが、計測・KPI・媒体の設計に抜けがないか不安」

## 5. サービスが提供する体験

### 基本フロー

```text
広告アカウントをOAuthで連携
        ↓
広告データ・KPI・キャンペーン状況を確認
        ↓
AIが変化、原因仮説、優先アクションを整理
        ↓
担当者が根拠・リスク・手順を確認
        ↓
人間が媒体管理画面または承認付きAPIで実行
        ↓
実施後の結果を確認し、次の改善へ
```

### 代表的な利用シーン

#### 1. 数値が悪化したとき

「CPAが悪化した理由と、次に確認することを教えて」と相談します。

AIは、費用・CV数・CVR・CPCなどに分解し、変化の大きい箇所、原因仮説、確認すべきレポート、作業手順を返します。原因を断定できない場合は、足りないデータと仮説を分けて表示します。

#### 2. 広告開始前に設計するとき

広告準備の質問票に、事業目標、商材、対象、予算、KPI、媒体、計測方法などを回答します。

AIはキャンペーンの作成案、根拠、実施前チェック、Google Ads管理画面で担当者が行う手順を作ります。キャンペーン自体は自動作成しません。

#### 3. 定期的に運用を振り返るとき

3日ごとの改善レポートで、KPI比較、変化、原因仮説、改善候補、優先度、手順、リスク、観察ポイントを確認します。メールは概要を届け、詳細は管理画面で確認します。

#### 4. 予算やキャンペーン状態を変更するとき

対象、現在値、変更後の値、理由、戻し条件を確認したうえで、人間が明示的に承認します。実行直前にも現在値を再取得し、想定と違えば停止します。

## 6. 主な機能の整理

| 機能 | 顧客にとっての価値 | AIがすること | 人間がすること |
| --- | --- | --- | --- |
| 広告アカウント連携 | APIキーを入力せず、広告データをサービスへつなげる | 連携された範囲の広告データを分析用に扱う | OAuthを許可し、対象アカウントを選ぶ |
| ダッシュボード | KPI、トレンド、異常、キャンペーンを一画面で見る | 数値の変化や異常を整理する | 対象期間・媒体・アカウントを選び、状況を判断する |
| AI Advisor | 「なぜ悪化したか」「次に何を見るか」を相談する | 結論、根拠、原因仮説、改善案、手順、リスク、自信度を作る | 根拠と手順を確認し、実施するか決める |
| 広告準備 | 開始前の抜け漏れを減らし、作成手順を作る | 回答からキャンペーン作成案と手順を作る | 媒体管理画面で確認し、必要な設定を作成する |
| 3日ごとの改善レポート | 定期的な確認と振り返りを習慣化する | 前期間比較、異常、仮説、優先アクションを作る | レポートを読み、チームで実施・観察する |
| 承認付き変更 | 変更内容を確認してから安全に実行する | status / budgetの変更候補を作る | 対象・現在値・理由・戻し条件を承認する |
| ヘルプ | KPI、OAuth、承認付き変更の注意点を確認する | — | 操作や運用ルールを確認する |

### ダッシュボードで見る情報

- 費用、表示回数、クリック、CTR、CPC、CV、CVR、CPA、売上、ROAS
- 前期間との比較
- 日別の費用、売上、CVの推移
- キャンペーン別の成果と状態
- CPA悪化、ROAS低下、CTR低下などの異常
- データの最終取得時刻、部分データ、同期エラー

### AI回答の型

LPで見せるAI回答は、単なるチャットの返答ではなく、次の構造を持つ業務回答として表現します。

1. 結論
2. 根拠
3. 原因仮説
4. 推奨アクション
5. 人間向け作業手順
6. 実施前チェック
7. リスク
8. 実施後の観察
9. 自信度

## 7. AIと人間の役割分担

### AIに任せること

- 連携済みの広告データを読む
- KPIの変化を比較・分解する
- 異常や確認優先度を整理する
- 原因仮説を複数提示する
- 推奨アクションと人間向けの手順を作る
- 広告開始前の質問回答から作成案をまとめる
- 実施前チェック、リスク、観察計画を作る
- 安定した業務方針やユーザーの好みを、条件を満たす場合だけ記憶候補にする

### 人間が担うこと

- AIが使う対象アカウントと範囲を許可する
- AIの根拠と原因仮説を確認する
- 施策を実施するか、見送るかを判断する
- 広告準備の作成案を媒体管理画面で確認・作成する
- Google Adsのstatus / budget変更を明示的に承認する
- 施策実施後の事業要因、LP変更、セール、在庫などを踏まえて結果を判断する
- 例外対応、社内合意、最終責任を引き受ける

### LPで必ず伝える境界

> AIが広告設定を勝手に変更することはありません。AIが分析・提案・作業手順を作り、人が確認・判断・実行します。

## 8. 安心設計とセキュリティ

公開ページでは、技術の羅列ではなく「何が起きないか」「誰が責任を持つか」を分かりやすく見せます。

- 広告媒体の連携はOAuthを基本とし、顧客にAPIキーやsecretの入力を求めない
- OAuth token、API key、service role keyなどをブラウザやAI回答へ出さない
- AIに渡すのは、workspaceの範囲を確認した広告指標や必要な業務コンテキストだけ
- AIの提案は実行済みとして扱わない
- Google Adsのstatus / budget変更は、認証、workspace範囲、契約プラン、明示承認、write flag、監査ログを通す
- 実行前に現在値を再取得し、競合や差分があれば実行を止める
- 実行後は変更前後、監査ID、戻しの関係を確認できる
- データ不足やGoogle認証切れがある場合、分析結果を捏造せず、再接続や確認が必要な状態にする

## 9. プランと料金

料金は現行要件で承認されている内容を掲載候補として整理します。Standard / PremiumのAI利用枠と相談回数目安は別承認が必要です。

| 項目 | ミニマム | スタンダード（主力） | プレミアム |
| --- | ---: | ---: | ---: |
| 初期費用 | 50,000円 | 70,000円 | 70,000円 |
| 月額 | 9,800円/月 | 49,800円/月 | 69,800円/月 |
| ユーザー数 | 2名 | 2名 | 5名 |
| Google Adsアカウント | 1件 | 3件 | 10件 |
| AI初期設定 | あり | あり | あり |
| AI改善レポート | 3日ごと | 3日ごと | 3日ごと |
| 通常AIチャット | 利用不可 | あり | あり・大きい利用枠 |
| Google Ads承認付き変更 | 利用不可 | あり | あり |
| 初期有人支援 | なし | なし | 予約制で含む |

### 料金の見せ方の仮説

- 主力はStandard。小規模チームが「自社で判断しながら広告運用を進める」ための基本プランとして見せる
- Minimumは、定期レポートと広告運用の基本確認から始めたい企業向け。ただしAIチャットと承認付き変更がロックされるため、LPでは制限を明記する
- Premiumは、複数アカウント・複数メンバー・有人支援が必要なチーム向け
- 無料トライアルは現行要件にないため、LPで「無料で試せる」とは書かない
- 年額プランは現時点で掲載しない

## 10. サービスページの推奨構成

これは、参考サイトの情報設計を取り入れながら、ちょこっとインハウスの正本に合わせたLP構成です。

### 1. ファーストビュー

**伝えること**: 広告の数字を見たあと、次の一手まで進められる。

仮見出し:

> 広告運用を、ちょこっとインハウス化。

補足:

> 自社で広告運用するチームのためのAI広告相談役。広告データを読み、原因仮説・改善案・人間向け作業手順まで作ります。

CTA候補:

- 実際の画面を見ながら相談する
- サービス資料を確認する
- 導入条件を相談する

### 2. 課題提示

「広告管理画面を見ても、次に何をすべきか分からない」という状況を、CPA悪化、レポート作成、優先順位の迷いに分解する。

### 3. 提供価値

> ちょこっとインハウスは、広告データを相談できる形に変えます。

OAuth連携 → AIが分析・提案 → 人が判断・実行 → 結果を振り返る、の4ステップを図解する。

### 4. できること

- 広告開始前の設計相談
- KPI・異常・キャンペーンの分析
- AI Advisorへの質問
- 優先度つきの作業手順
- 3日ごとの改善レポート
- Google Adsの承認付きstatus / budget変更

### 5. 人間が主役の安心設計

AIがしないことを先に明示する。

- AIは広告設定を勝手に変更しない
- キャンペーン作成は自動実行しない
- AIの提案は必ず人が確認する
- 変更には対象・現在値・理由・戻し条件を表示する

### 6. 利用イメージ

質問例「CPAが悪化した理由と、次に確認することを教えて」に対して、結論・根拠・原因仮説・作業手順・自信度が返る画面を見せる。

### 7. 導入・料金

初期費用、月額、対応アカウント数、AIチャットの利用可否、承認付き変更の範囲を表で示す。Standardを主力として、向いている企業像を添える。

### 8. CTA

単なる「お問い合わせ」ではなく、次の相談内容まで指定する。

> 自社の広告運用で、どの数字を見て、何を判断し、誰が実行しているか。実際の運用フローを見ながら、最初にAIへ任せる範囲を一緒に整理します。

## 11. 参考LPから取り入れるデザイン方針

参考にしたサイト:

- [Askhub](https://askhub.jp/): 一つの大きな約束、プロダクト画面を使ったファーストビュー、資料請求と相談の2導線、ABOUT / FEATURES / SUPPORT / FAQの流れ
- [AD EBiS](https://www.ebis.ne.jp/): 数字や課題を起点にしたファーストビュー、課題提示、番号付きの「選ばれる理由」、機能、導入支援、料金、FAQ、複数のCTA

### 採用する構造

1. ヘッダー: ロゴ、ページ内アンカー、主CTA
2. ファーストビュー: サービスの約束、短い説明、2つのCTA、プロダクト画面
3. 信頼補助: 対応範囲と「AIが勝手に変更しない」設計
4. 課題: 顧客が日々感じている3つの詰まり
5. 解決の流れ: 連携 → AIの整理 → 人の判断・実行 → 振り返り
6. 選ばれる理由: 番号付きで、機能ではなく業務上の変化を説明
7. 利用イメージ: 実際の質問とAI回答の構造
8. 安心設計・導入: 人間の確認範囲、セキュリティ、導入時の進め方
9. 料金: 3プランとStandardの位置づけ
10. FAQ: 対応媒体、AIの実行範囲、データ・セキュリティ、料金・導入条件
11. 最終CTA: 相談内容が分かる相談導線

### 採用する見せ方

- 白〜薄いグレーをベースに、既存UIの緑・ティールを主アクセントにする
- ファーストビューは左に短いコピー、右にダッシュボード / AI回答のプロダクト画面を置く
- 長い説明を連続させず、課題カード、番号付き理由、比較表、業務フローで区切る
- CTAは「資料を見る」と「実際の画面を見ながら相談する」の2種類を基本にする
- 画面モックには、結論・根拠・原因仮説・作業手順・自信度を表示し、価値が一目で分かるようにする
- 既存UIの安心感を活かし、過度なグラデーションや派手な未来感は使わない
- 参考サイトのロゴ、実績数値、表現を流用しない。自社で検証できるproofだけを使う

### 採用しない構造

- 導入社数や改善率の実績セクション（実証データが揃うまで）
- 「AIがすべて自動で運用する」という訴求
- Google / Meta / Yahooがすべて本番対応済みと受け取られる媒体一覧
- 実績がない状態での顧客ロゴ帯
- 無料トライアルを前提にしたCTA

## 12. LPの確定構造・確定文言

以下をLP実装時の初稿にそのまま使用します。レイアウト調整のための改行・文字量調整は可能ですが、主張の順番と意味は変えません。

### Header

- ロゴ: `ちょこっとインハウス`
- ナビ: `サービス概要` / `できること` / `安心設計` / `利用イメージ` / `料金` / `FAQ`
- 主CTA: `サービス資料を見る`

### 01. Hero

**Eyebrow**

> 自社で広告運用するチームのためのAI広告相談役

**H1**

> 広告運用を、ちょこっとインハウス化。

**Lead**

> 広告管理画面の数字を、次の一手に変える。

**Body**

> 広告データを読み取り、変化の理由や確認する順番、優先度の高い作業手順までAIが整理します。人が確認・判断・実行するから、社内の広告運用を少しずつ強くできます。

**CTA**

- Primary: `サービス資料を見る`
- Secondary: `実際の画面を見ながら相談する`

**Safety note**

> AIが広告設定を勝手に変更することはありません。

**Hero visual**

ダッシュボード、AI Advisor、やることリスト、データ連携状況を一つのプロダクト画面として表示する。数値は架空データであることを画面外の注記またはデモ表示で分かるようにする。

### 02. Trust strip

**見出し**

> まずは広告データを読み取り、判断に必要な材料をそろえる。

**表示要素**

- `Google Ads 先行対応`
- `OAuth連携`
- `人間の確認・承認`
- `監査ログ`

Meta Ads / Yahoo Adsは、公開時点の実装状況を確認したうえで「今後対応」または非表示とする。

### 03. Problem

**H2**

> 広告管理画面を見ても、次の一手がわからない。

**Intro**

> 数字は見えている。けれど、どこから確認し、何を優先し、誰が動くかまでは決まらない。広告運用で時間がかかるのは、数字を見ることより、その後の判断です。

**Card 01**

- Title: `数字は見ているけど、次に何をすべきかわからない`
- Body: `CPAやROASが変化しても、まず確認する指標やレポートが絞れず、判断が止まってしまう。`

**Card 02**

- Title: `分析やレポート作成に時間がかかる`
- Body: `日々の集計や説明資料づくりに追われ、改善施策を考えて実行する時間が残らない。`

**Card 03**

- Title: `施策の優先順位に自信が持てない`
- Body: `候補は出せても、なぜ今それをやるのか、どのリスクがあるのかを社内に説明しにくい。`

### 04. Solution flow

**H2**

> 広告データを、相談できる形に。

**Body**

> ちょこっとインハウスは、広告データの変化を読み取り、原因仮説・確認事項・人間向けの作業手順へ整理します。実施するかどうかは、担当者が根拠とリスクを確認して決めます。

**Step 01**

- Title: `広告アカウントをOAuthで連携`
- Body: `必要な範囲の広告データを、APIキーの入力なしでつなぎます。`

**Step 02**

- Title: `AIが変化と原因仮説を整理`
- Body: `KPIの比較、異常、確認するレポート、原因の候補をまとめます。`

**Step 03**

- Title: `人が判断して実行`
- Body: `作業手順・リスク・戻し条件を確認し、担当者が媒体管理画面または承認付きAPIで実行します。`

**Step 04**

- Title: `結果を確認して次の改善へ`
- Body: `実施後のKPIと事業側の変化を見て、次の判断に活かします。`

### 05. Reasons / Features

**H2**

> ちょこっとインハウスが支援する4つのこと

**01 — 広告の変化を、確認する順番に**

> 費用、CV、CPA、CTR、CPC、CVR、ROASなどの変化を比較し、どの指標やキャンペーンから確認するかを整理します。数字を並べるだけでなく、次に見る場所を明確にします。

**02 — 施策を、実行できる手順に**

> 推奨アクションを、担当者が確認できる手順へ落とします。実施前チェック、リスク、実施後に観察する指標まで一つの回答にまとめます。

**03 — 広告開始前の迷いを、作成案に**

> 一問一答の広告準備で、事業目標、商材、対象、予算、KPI、媒体、計測方法を確認します。AIはキャンペーン作成案と手順を作りますが、キャンペーン自体は自動作成しません。

**04 — AIは提案、人が判断**

> AIが広告設定を勝手に変更することはありません。Google Adsのstatus / budget変更も、対象・現在値・理由・戻し条件を確認し、人が明示的に承認した場合だけ実行します。

### 06. Use case / Product demo

**H2**

> たとえば、CPAが悪化したとき。

**Question**

> CPAが悪化した理由と、次に確認することを教えて。

**Answer structure**

- 結論: `CPA悪化の主因を、CVRとCPCの変化に分けて確認します。`
- 根拠: `前期間との比較、キャンペーン別の費用・CV・CPC・CVRを確認します。`
- 原因仮説: `検索意図のずれ、LPの表示速度、競合によるCPC上昇などを候補にします。`
- 作業手順: `検索語句レポート、LP、計測状態を順番に確認します。`
- 自信度: `データの範囲と取得時刻を踏まえて表示します。`

**Section close**

> 答えを出して終わりではなく、担当者が次に確認できるところまで整理します。

### 09. FAQ

**Q. AIが広告設定を自動で変更しますか？**  
いいえ。AIは分析、提案、作業手順の作成を行います。Google Adsのstatus / budget変更は、対象・現在値・理由・戻し条件を人が確認し、明示的に承認した場合だけ実行します。キャンペーン作成は自動実行しません。

**Q. どの広告媒体に対応していますか？**  
Google Adsを先行して対応します。Meta Ads / Yahoo Adsは、公開時点の対応状況に合わせて案内します。

**Q. APIキーを渡す必要がありますか？**  
基本の連携はOAuthで行います。OAuth tokenやAPIキーなどの秘密情報をAI回答やブラウザに表示しない設計です。

**Q. どのような質問をAIにできますか？**  
「CPAが悪化した理由」「次に確認する指標」「広告開始前に見直す項目」など、広告データの変化や運用手順について相談できます。

**Q. 無料トライアルはありますか？**  
現行プランでは無料トライアルを設定していません。料金や導入条件は、サービス資料または相談で確認できます。

## 14. LPで使えるコピーの方向性

### 主メッセージ

- 広告管理画面の数字を、次の一手に変える
- 分析で止まらず、実行できる手順まで
- AIが整理し、人が判断する広告運用
- 自社運用の判断を、少しだけ強くする

### 機能ではなく価値で説明する言い換え

| 機能の言い方 | LPでの価値表現 |
| --- | --- |
| KPI分析 | 数字の変化を、確認する順番に変える |
| 原因仮説 | 「なぜ悪くなったか」を仮説として切り分ける |
| Human Task | 次にやることを、担当者が動ける手順にする |
| OAuth連携 | APIキーを渡さず、必要な広告データをつなぐ |
| 承認付きwrite | 変更前の値と戻し条件を確認してから実行する |
| 定期レポート | 定期的に広告の変化と次の判断を見直す |

### 避ける表現

- AIが広告運用を全部自動化する
- AIが最適な施策を自動で実行する
- 完全自動運用
- 必ずCPAが改善する
- 広告費を削減できる
- どんな広告アカウントでも対応できる
- Google / Meta / Yahooにすでに本番対応していると読める表現（現行正本と公開時の実装状況を確認するまで）

## 15. 現時点で使えるproofと、使えないproof

### 使えるproof

- リポジトリ上の実装方針: AI回答の必須構造、no-write境界、承認付き変更の条件
- 実装済みとして整理されている画面・API・Agent Serviceの構造
- 架空データによるデモ: KPI、異常、AI回答、広告準備、承認レビューの流れ
- 広告運用の具体的な確認観点: CPAをCPC / CVRに分解する、検索語句を確認する、LP表示速度や計測欠損を確認するなど

### まだ使えないproof

- 顧客名、顧客ロゴ、導入社数、改善率、削減時間などの実績値
- 本番環境での継続運用実績
- Google / Meta / Yahooすべての本番連携が完了しているという主張
- 「成果が出る」「CPAが改善する」といった成果保証
- `fixtures/demo/` の架空データを実績として見せること
